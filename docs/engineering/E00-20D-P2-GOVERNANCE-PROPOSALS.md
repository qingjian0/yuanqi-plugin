## 1. FIX-018：统计去重与重放口径

### 问题
`event_count`、统计快照、事件重放和消费端去重可能混用同一个“数量”概念，导致重复投递、重放、投影重建时统计漂移。

### 建议裁决
将统计口径分成不同指标，不再使用含义不明的通用计数：

| 指标 | 建议定义 | 重放行为 |
|---|---|---|
| `committed_event_count` | 指定 stream 与统计窗口内，已提交的事件记录数 | 读取历史事件不增加原始计数 |
| `unique_event_count` | 按稳定 `event_id` 去重后的事件记录数 | 同一 event_id 不重复计数 |
| `projection_record_count` | 某投影当前实际记录数 | 重建投影时重新计算 |
| `delivery_attempt_count` | 消费端收到/尝试处理的投递次数 | 每次投递尝试均可计数 |
| `deduplicated_delivery_count` | 因已处理 event_id 而跳过的重复投递数 | 重复投递可增加此计数 |

### 去重规则
1. 去重键优先使用稳定 `event_id`；不得用时间戳、payload 哈希或数组位置替代事件身份。
2. 去重记录必须限定作用域，至少明确 consumer/subscription 与 event stream；不能把一个消费者的处理状态误用为另一个消费者的状态。
3. 同一事件重复投递时，业务副作用不得重复执行；处理状态与副作用应处于可恢复的一致性边界。
4. Event replay 保留原始 `event_id`、`stream_id` 和 sequence；重放不是创建新事件。
5. 投影重建必须声明 checkpoint/起点，并以确定性 reducer 重算；不得把重建过程伪装成新的原始事件。
6. 统计窗口必须显式给出起止边界、时区/时间基准、stream 范围和过滤条件。
7. 若历史数据缺少稳定 event_id 或 checkpoint，统计结果标记为不完整/不可比，不得猜测补齐。

### 仍需裁决
- `event_id` 的全局唯一性范围（全局、租户或 stream）需与原始 ID 规范核对。
- 统计快照是否属于领域事实、运行指标或派生投影，需由对应 Owner Domain 确认。
- 内部统计字段不应自动暴露到普通用户对话或公共 API；尤其不得把内部序列/计数实现细节当作业务事实。

### 验收证据
需要真实事件存储/消费者实现及测试覆盖：重复投递、跨消费者隔离、重放、checkpoint 恢复、投影重建、窗口边界和并发处理。当前无测试源码，状态为 NOT IMPLEMENTED / NOT VERIFIED。

## 2. FIX-019：Schema URI 与版本策略

### 问题
Schema 缺少统一、稳定且不可变的标识策略，会造成引用漂移、缓存污染和历史消息无法按原版本解释。

### 建议裁决
1. 每个可独立引用的 Schema 使用唯一 `$id`；`$id` 标识 Schema 身份，不承担下载地址或授权功能。
2. URI 命名空间必须由项目正式控制的域名/URN 命名空间确定。当前仓库资料没有足够证据确认可长期控制的域名，因此暂不冻结具体生产 URI。
3. 版本路径采用不可变版本：已发布版本不得原地修改；任何语义或校验行为变化均发布新版本。
4. 建议将协议版本、Schema 版本和业务事件类型版本分离：
   - `protocol_version`：消息协议兼容边界；
   - Schema `$id` / schema version：结构定义版本；
   - `event_type_version`：业务事件语义版本。
5. JSON Schema Draft 2020-12 的方言声明使用标准 URI；公共 Schema 的 `$schema` 固定为 Draft 2020-12。
6. `$ref` 必须指向仓库内可解析的已登记 Schema 或正式发布的不可变 URI；禁止引用浮动的 `latest`、默认分支或可变别名作为规范依赖。
7. 兼容性声明必须区分向后兼容、向前兼容和不兼容；不能仅凭版本号大小推断。
8. Schema 发布清单应记录 `$id`、文件路径、摘要、版本、状态、兼容关系和发布日期。

### 暂不决事项
- 生产命名空间（域名或 URN）待项目所有者确认。
- Schema 文件路径和版本号采用 major-only 还是完整 semver，需结合实际兼容策略确定。
- 发布仓库/制品地址待发布流程建立后确定。

### 验收证据
需要 Schema registry/index、重复 `$id` 检查、引用完整性检查、不可变发布测试及兼容性测试。当前没有 Schema 文件或验证流水线，状态为 NOT IMPLEMENTED / NOT VERIFIED。

## 3. FIX-020：ADR 编号、状态与索引治理

### 当前可核实事实
- 当前 `dev` Git Tree 已有 `docs/adr/README.md` 治理说明，但没有正式 ADR 决策记录文件。
- 既有工程文档提到“ADR-001～290 候选项”，但当前可见 Tree 未包含这 290 项候选项的原始清单或逐项内容。
- 因缺少候选项原始清单，当前不能核实重复编号、同义决策、冲突、依赖或实际状态；不得凭空生成 290 条记录，也不得据此认定编号 001～290 均已占用。

### 建议治理规则
1. 一个 ADR 编号只对应一个决策主题；编号本身不代表批准。
2. 采用固定宽度编号（建议四位，如 `ADR-0001`），按首次登记顺序递增；编号分配后不回收、不复用。
3. 新 ADR 必须登记在唯一索引中；索引记录编号、标题、领域、状态、日期、Owner、关联 FIX/CR、替代关系和实现证据。
4. 状态采用以下互斥阶段：
   - `PROPOSED`：待审议，不具约束力；
   - `ACCEPTED`：已批准，成为当前决策；
   - `REJECTED`：已明确不采纳；
   - `SUPERSEDED`：被后续 ADR 替代，保留历史；
   - `DEPRECATED`：不再推荐，但尚无完整替代决策。
5. `IMPLEMENTED` 与 `VERIFIED` 是实现/验证成熟度，不是决策状态；应作为独立字段记录，不能与 ACCEPTED 混为一谈。
6. 已 ACCEPTED 的 ADR 不直接改写其决策内容。实质性改变应新增 ADR，并将旧 ADR 标记为 SUPERSEDED；纯勘误应保留修订记录。
7. ADR 至少包含：标题、状态、日期、背景、决策、备选方案、后果、约束/不做事项、证据、关联项和复审条件。
8. ADR 只记录架构级、长期影响的决策。字段级细节放 Schema/契约文档；测试实现细节放测试文档。
9. 未经批准的建议稿继续放在 `docs/engineering/`，不得伪装成正式 ADR。
10. 冲突审查必须同时检查：相同决策重复、同一边界互斥、上下游依赖循环、被替代决策仍被引用、状态与实现证据不一致。

### 对“ADR-001～290”的处理
建立候选项导入门槛，而不是直接创建 290 个空文件：
- 输入必须是原始候选清单、历史文档或可追溯提交；
- 为每项保留原始标题、来源、原编号和原状态；
- 先生成去重/冲突报告，再分配正式 ADR 编号；
- 未能找到来源的编号标记为 `UNVERIFIED_REFERENCE`，不视为已占用或已批准；
- 当前先不分配下一正式编号，直到候选清单核验完成。

### 验收证据
需要原始候选清单、正式 ADR 索引、模板、编号唯一性检查、链接检查和状态一致性检查。当前仅建立治理建议与 ADR 流程说明，未创建正式 ADR 决策记录，状态为 NOT IMPLEMENTED / NOT VERIFIED。
